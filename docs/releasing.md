# 发布与仓库同步

源码、构建产物和签名凭据分别管理。GitHub 计划作为主仓库，Gitee 同步同一份源码；本地整理不代表已公开发布。

## 首次公开前

1. 运行 scripts/check-public-files.py，检查将要提交的文件及第三方许可证。
2. 检查 README 平台状态、构建方法和功能描述是否与源码一致。
3. 创建仓库后检查暂存 diff；若导入已有历史，单独扫描全部历史。
4. 确认后才推送源码。不要上传整个工作目录或证书资料。

.gitignore 只阻止未跟踪文件被默认添加，无法移除已有历史中的秘密。发现泄露时应撤销相关凭据并清理历史，不能仅补一条忽略规则。

## 双平台版本

同一版本可以在 Releases 附上 macOS DMG 与 Windows 安装包；两端进度不同可以独立打标签和发布。发行说明须标明系统要求、架构、改动、已知限制和 SHA-256。不要为未实现的 Windows 版提供占位安装包或虚假的下载链接。

macOS 普通源码构建使用临时签名即可。正式分发需要维护者自己的 Developer ID 签名、公证和票据附加；这些凭据保存在本机或受保护的 CI secrets 中，绝不写入仓库。Windows 签名和安装流程在框架确定后补充。

构建命令不会自动公证或生成 DMG。正式发行应先验证版本与测试结果，再单独执行发布流程。

## GitHub 与 Gitee

维护一份主历史，向 GitHub 推送后再同步 Gitee。避免两边分别维护不同代码。自动化前可以手动向两个远程推送同一分支和标签；不要随意使用强制镜像推送，以免删除目标仓库内容。

代码同步不等于 Issue、合并请求、Release 附件同步。安装包和发行说明需要单独发布或提供明确的下载入口。仓库正式建立后再补充真实链接，不预填未经确认的地址。
